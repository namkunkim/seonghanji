## 0. 이 문서가 답하는 질문

기획 문서 31개는 **「무엇을 만들 것인가」**에 답한다.
이 문서는 **「그것을 실제로 만들려면 그 밖에 무엇이 필요한가」**에 답한다.

**이 문서가 다루지 않는 것**

| 제외 | 이유 |
|---|---|
| 시나리오·수치·물량 | `JOBS.md` 큐 12개로 전부 종료됨 |
| 게임 규칙의 재설계 | 불가침 원칙(`CLAUDE.md` §2)에 걸린다 |
| 구체적 코드 | 아직 아키텍처 결정 전이다 |

**이 문서가 다루는 것** — 기술 아키텍처 · 데이터 정본화 · 검증 도구 · 아트/사운드/텍스트 물량 ·
라이브 운영 · 법무 · QA · 조직과 일정.

## 2. 기술 아키텍처 — 코드 한 줄 전에 정할 것 넷

### 2.1 결정 ①: 시간은 누가 소유하는가 [최우선]

이 게임에서 **시간은 자원이고, 그 자원은 팔지 않기로 확정되어 있다**
(`time-and-monetization.md` §8.1 불가침 ①).

그렇다면 **시간을 훔치는 것이 이 게임 최대의 부정행위**가 된다.
기기 시계를 세 시간 앞당기면 대회랑을 공짜로 돌파한다. 과금으로 못 사는 것을 조작으로 얻는다 —
불가침 원칙이 클라이언트에서 무너진다.

> **결론: 게임 내 시각·항행 완료 시각·명령 예약은 전부 서버가 소유한다. 예외 없다.**
> 클라이언트 시계는 **표시 보간**에만 쓰고, 완료 판정에는 절대 쓰지 않는다.
>
> **→ 2026-08-24 정본 등재: `DECISIONS.md` V-24.**

이 하나가 「완전 오프라인 단독 실행」 선택지를 지운다. **서버는 선택이 아니라 전제다.**

### 2.2 결정 ②: 세계를 어떻게 굴리는가 — 지연 산출 대 상시 틱

| 모드 | 세계 | 권고 모델 | 근거 |
|---|---|---|---|
| **싱글 캠페인** | 플레이어 1인 전용 | **지연 산출(lazy)** | 접속 시점에 「마지막 정산 시각 → 현재」를 한 번에 계산. 미접속 3일도 한 번의 연산 |
| **시즌 대전** | 3~8인 공유 | **상시 틱(authoritative tick)** | 남의 함대가 내 접속과 무관하게 움직여야 한다 |

싱글에서 상시 틱을 돌리면 **동시 접속자 수가 아니라 누적 가입자 수만큼 서버가 돈다.**
AI 결정 주기가 실제 1~3시간(`ai-design` §10)이므로 지연 산출로 충분하다.

> **다만 알림은 지연 산출로 안 된다.** 「항행 완료」를 알리려면 그 시각에 서버가 깨어 있어야 한다.
> → **예약 잡 스케줄러**를 따로 둔다. 세계는 자지만, 알람 시계는 깨어 있다.

### 2.3 결정 ③: 시뮬레이션 코어를 어디에 두는가

전투 미리보기·편성 결과 예측을 클라이언트가 보여주려면, 클라이언트와 서버가 **같은 규칙**을 알아야 한다.
규칙을 두 벌 쓰면 반드시 어긋난다.

> **권고: 엔진 비의존 순수 라이브러리 한 벌.** 클라이언트가 참조하고, 서버도 같은 것을 참조하고,
> 헤드리스 시뮬레이터도 같은 것을 참조한다.

**결정론 요건** — 같은 입력·같은 시드면 어느 기기에서든 같은 결과가 나와야 한다.

| 요건 | 이유 |
|---|---|
| 부동소수점 금지 (정수 또는 고정소수) | 기기별 부동소수 오차가 전투 결과를 뒤집는다 |
| 시드 기반 난수 · 시드 저장 | 복귀 브리핑 재현 · 분쟁 처리 · 버그 재현 |
| 난수 소비 순서 고정 | 순서가 바뀌면 결정론이 깨진다 |
| 컬렉션 순회 순서 고정 | 해시 순회는 플랫폼마다 다르다 |

**결정론이 주는 부수 효과** — 세이브가 「상태」가 아니라 「시드 + 명령 로그」가 될 수 있다.
용량이 작고, 재생 가능하고, 조작 탐지가 쉽다.

### 2.4 결정 ④: 5.8개월짜리 세이브를 어떻게 지키는가 [고유 위험]

캠페인 완주가 **348시간 · 하루 2시간 기준 약 5.8개월**이다(`time-and-monetization.md` §8-10).
**그 사이에 밸런스 패치가 반드시 나간다.**

> 사기 산식을 고치면, 석 달째 진행 중인 플레이어의 세계는 어떻게 되는가?

| 방안 | 평가 |
|---|---|
| 무조건 최신 규칙 적용 | 진행 중 캠페인이 뒤틀린다. 5.8개월을 부은 플레이어가 이탈한다 |
| **규칙 집합 버전 고정(pinning)** | **권고.** 세이브에 규칙 버전을 새기고, 캠페인은 시작 시 버전으로 끝까지 간다 |
| 시나리오 경계에서만 승격 | 절충. 시나리오 6개가 자연스러운 이행 지점이다 |

권고안의 대가: **규칙 버전을 여러 개 동시에 유지해야 한다.** 이것을 나중에 붙이는 것은 사실상 불가능하다 —
**M0에서 데이터 스키마와 함께 설계에 넣어야 한다.**

## 3. 데이터 정본화 — 문서는 데이터가 아니다

### 3.1 문제

수치가 전부 마크다운 표 안에 있다. 사람은 읽지만 기계는 못 읽는다.
그리고 **같은 수치가 여러 문서에 중복**되어 있다 — 사기 범위 0~100 대 45~125의 어긋남이
한동안 방치됐던 것이 그 증거다(`HANDOVER.md` 머리말).

### 3.2 권고 — 역할 분리

```
docs/*.md        ← 근거(왜 이 값인가). 사람이 읽는다. 정본 아님
data/*.json      ← 값(무엇인가). 기계가 읽는다. 정본
schema/*.json    ← 값의 형식. 검증기가 읽는다
```

> **문서가 정본이면 코드가 문서를 파싱해야 한다. 그 길로 가면 안 된다.**
> 대신 **문서에서 데이터를 한 번 추출**하고, 이후로는 **데이터가 정본**이며,
> 문서는 ID(`F-16` 같은)로 근거를 가리킨다.

### 3.3 필요한 데이터셋

| 데이터셋 | 규모 | 출처 문서 |
|---|---|---|
| 성계 | 19 | `star-map.md` |
| 권역 | 45 (국력 · 전화 계수 · 인접) | `region-power.md` |
| 회랑·항로 | 15 + 항로망 | `star-map.md` |
| 인물 | **492** (명장 150 + 일반 249 + 이역 93) × 5스탯 · 성향 · 특성 | `generals-stats` · `officers-256` · `foreign-90-stats` |
| 인물 배치 | 399 × 6시나리오 | `character-assignments.md` |
| 함종·진형 | **함종 6** · 진형 7 | `ship-specs.md` — ⚠ **함급은 5다.** 「함급 6」은 오기였다 (2026-08-24 정정) |
| 기능 이벤트 | 40 (조건식 · 임계값) | `function-events.md` |
| ACT | 68 (소요 · 유형) | `time-and-monetization.md` §3.4 |
| 시작 배치 | 21 (세계 상태 × 시나리오) | `world-state-setup.md` |
| 엔딩·변주 | 사분면 4 + 특수 5 · 변주 48문단 | `endings` · `ending-variations` |
| 텍스트 | 이벤트 40 · 막간 35 · 후일담 10 · 프롤로그 | `05-narrative/*` |

### 3.4 ID 체계 [미정 — 결정 필요]

`function-events.md`의 `F-01`~`F-40`이 유일하게 존재하는 ID 체계다. 나머지는 이름으로만 불린다.
**이름은 키가 될 수 없다** — 동명이인이 있고, 번역하면 바뀐다.

| 대상 | 제안 접두사 |
|---|---|
| 인물 | `CHR-0001` ~ |
| 권역 | `RGN-01` ~ `RGN-45` |
| 성계 | `SYS-01` ~ `SYS-19` |
| 회랑 | `COR-01` ~ `COR-15` |
| 기능 이벤트 | `F-01` ~ `F-40` (기존 유지) |
| ACT | `ACT-S1-01` 형식 |
| 문자열 | `str.<화면>.<키>` |

### 3.5 정합성 검증기 [필요]

데이터 정본화의 대가로 **문서와 데이터가 갈라질 위험**이 생긴다. 이것을 사람이 지킬 수는 없다.

| 검사 | 예 |
|---|---|
| 참조 무결성 | 배치표의 인물 ID가 인물 데이터에 존재하는가 |
| 총량 | 권역 45 · 성계 19 · 회랑 15가 맞는가 |
| 범위 | 사기 0~125 · 천명 0~100을 벗어난 값이 없는가 |
| 도달성 | 모든 권역이 항로망으로 도달 가능한가 (`star-map.md` 교착 방지) |
| 미사용 | 한 번도 참조되지 않는 이벤트·인물·텍스트가 있는가 |

## 4. 클라이언트·서버 기술 선택

### 4.1 이 게임이 요구하는 것 / 요구하지 않는 것

| 요구함 | 요구하지 않음 |
|---|---|
| 대량의 목록·표·텍스트 UI | 3차원 실시간 렌더링 |
| 지도 표시 (성도 19노드 · 파이 차트 · 확대축소) | 물리 연산 |
| 배터리 효율 (세션 3~5분 × 하루 여러 번) | 프레임 정밀 입력 |
| 푸시 알림 · 인앱 결제 · 오프라인 동기화 | 고사양 셰이더 |

**이것은 렌더링 문제가 아니라 UI·데이터 문제다.** 엔진 선택 기준이 액션 게임과 다르다.

### 4.2 엔진 후보

| 후보 | 장점 | 단점 |
|---|---|---|
| **Unity 6.x** | 모바일 배포 성숙 · 결제/알림/분석 도구 생태계 · 국내 인력 풀 최다 · 서버를 같은 언어(.NET)로 쓰면 **시뮬레이션 코어 한 벌 공유 가능**(§2.3) | 대량 텍스트 UI가 강점 분야는 아님 · 상용 좌석 비용 |
| Godot 4.x | 무료·개방 라이선스 · 2차원 UI에 강함 · 빌드 경량 | 모바일 결제/알림이 플러그인 의존 · 국내 인력 풀이 좁다 · 대형 라이브 서비스 사례 부족 |
| 네이티브 + 공용 코어 | UI 품질·배터리 최상 | 두 플랫폼을 각각 만든다. 개발 비용 약 2배 |

> **권고: Unity 6.x + .NET 서버.**
> 결정적 이유는 그래픽이 아니라 **§2.3의 코어 공유**다. 클라이언트·서버·시뮬레이터가
> 같은 규칙 라이브러리를 참조할 수 있는 조합이 비용을 가장 크게 줄인다.
> 2024년 9월 런타임 수수료가 철회되고 좌석 구독으로 돌아갔으므로, 매출 연동 비용 위험도 해소됐다.

### 4.3 서버 구성 요소

| 요소 | 역할 |
|---|---|
| 인증·계정 | 스토어 계정 연동 · 기기 이전 · **계정 삭제**(스토어 필수 요건) |
| 시간 권위 | 게임 내 시각 · 완료 판정 · 시계 조작 방어 |
| 세계 상태 저장 | 캠페인 세이브 · 규칙 버전 고정 · 스냅숏 |
| 명령 큐 | 예약 명령 접수 → **실행 시점 재검증** (그 사이 상황이 바뀐다) |
| 지연 산출 엔진 | 접속 시 「마지막 정산 → 현재」 일괄 계산 |
| 예약 잡 스케줄러 | 푸시 알림 발송 시각 관리 (야간 23~07시 금지 규칙 포함) |
| 결제 | 영수증 검증 · 중복 지급 방지 · 환불 회수 |
| 뽑기 | **서버 판정 필수** · 확률표 버전 관리 · **감사 로그**(§7.2) |
| 시즌 | 상시 틱 · 방 편성 · 시즌 종료 정산 |
| **자산 계승** | 싱글에서 축적한 **인물·기술·명성이 시즌으로 넘어간다** (`design-overview.md` §6.4). 두 모드가 세이브를 공유하지 않으므로 **어디까지 넘기는가**를 명시적으로 정의해야 하며, 규칙 버전 고정(§2.4)과도 얽힌다 |
| 운영 도구 | 계정 조회 · 보상 지급 · 되돌리기 · 제재 |
| 원격 설정 | 밸런스 계수 · 이벤트 일정 (클라이언트 배포 없이 조정) |

### 4.4 성능·기기 예산 [미정 — 측정 필요]

|---|---|

> **인물 492를 전부 전용 그림으로 그리면 프로젝트가 아트 비용에 지배당한다.**
> 그런데 **492도 전부가 아니다** — 초빙권 뽑기 풀의 **창작 재야 인물이 「수백 명」** 더 있다
> (`design-overview.md` §8.4).

**권고 — 4계층**

| 계층 | 인원 | 처리 |
|---|---|---|
| 명장 | 150 | 전용 그림 |
| 일반 무장 | 249 | **부품 조합형** (얼굴·복식·배경 조합) |
| 이역 인물 | 93 | 부품 조합형 (문화권별 부품 세트) |
| **재야·창작** | **수백** | **런타임 절차적 생성** — 부품 조합을 코드가 굴린다 |

**근거 둘.**

1. `ui-design.md` §2가 이미 **「일반 무장 256은 개별 관리 불가 · 자동화 필수」**라고 판정했다.
   개별 관리하지 않는 인물에 개별 그림을 붙이는 것은 균형이 맞지 않는다.
2. **부품 파이프라인은 비용 절감 선택지가 아니라 설계가 이미 요구하는 것이다.**
   `design-overview.md` §8.4가 재야를 **「절차적 생성 + 일부 수작업 개성 부여」**로 못박았고,
   그 인물들은 **뽑기로 무한히 생성**되므로 그리는 방식 자체가 성립하지 않는다.

> **즉 부품 시스템은 「지을지 말지」가 아니라 「이미 지어야 하는 것」이다.**
> 일반 무장 249와 이역 93을 거기에 얹는 것은 **추가 비용이 아니라 재사용**이다.
> 이것이 4계층 권고의 실제 근거이며, 3단 차등으로 적었던 초판보다 결론이 더 강하다.

## 7. 법무·규정 준수

> 이 절은 조사에 근거한 요약이며 **법률 자문이 아니다.** 출시 전 전문가 검토가 필요하다.

### 7.1 등급분류 (국내)

오픈마켓 모바일 게임물은 **자체등급분류 사업자**를 통한 분류가 일반적이며,
게임물관리위원회에 직접 신청하는 경로도 있다(통상 10~15일). 전체이용가 / 12세 / 15세 / 청소년이용불가.

**이 게임의 쟁점** — 확률형 아이템(초빙권 뽑기)이 있고, 전쟁 묘사가 있다.
**12세** 또는 **15세** 판단이 필요하며, 등급에 따라 청소년 보호 요건이 달라진다.

### 7.2 확률형 아이템 표시 의무 [중대]

게임산업법 개정으로 확률 정보 공개가 의무화되었고(위반 시 2년 이하 징역 또는 2천만원 이하 벌금),
**2026년 8월 1일 시행분에서 누락·허위 표시에 최대 3배 손해배상과 입증책임 전환이 추가되었다.**

**입증책임이 게임사에 있다**는 것은 곧바로 기술 요건이 된다.

| 요건 | 구현 |
|---|---|
| 게임 내·홈페이지·광고에 확률 표시 | 확률표를 **데이터로 관리**하고 표시 화면이 그것을 직접 읽는다 (수기 게시 금지) |
| **확률표 버전 관리** | 언제부터 언제까지 어떤 확률이었는지 남는다 |
| **뽑기 감사 로그** | 어떤 요청이 어떤 시드로 무엇을 뽑았는지 보존 |
| 서버 판정 | 클라이언트 판정은 입증이 불가능하다 |

> **초빙권이 「인물」이 아니라 「기회」를 판다는 설계**(`design-overview.md` §8.6)는
> 표시 의무 관점에서도 유리하다 — 확률의 대상이 명확히 분리된다.
> 다만 **등용 3중 판정의 성공률도 표시 대상인지**는 판단이 필요하다 (§11 검토 포인트 3).

## 8. QA — 이 게임 고유의 시험 불가 문제

> **캠페인 1회 완주가 348시간이다. 실시간으로는 시험할 수 없다.**

한 번의 회귀 시험에 5.8개월이 걸린다면 QA가 성립하지 않는다.

**필수 요건 — 서버측 가상 시계**

시간을 서버가 소유하기로 했으므로(§2.1), **시간 배속도 서버 기능이어야 한다.**
개발·QA 환경에서 60배 ~ 1만 배속과 임의 시각 주입이 가능해야 한다.

> ⚠ **이것을 나중에 붙일 수 없다.** 시간 소유 구조를 짜는 그 순간에 함께 설계해야 한다.
> 그리고 **이 기능은 상용 빌드에 절대 존재하면 안 된다** — 존재하는 순간 불가침 원칙 ①이 무너진다.

**시험 항목**

| 유형 | 내용 |
|---|---|
| 결정론 | 같은 시드 → 같은 결과. 기기·플랫폼 교차 검증 |
| 시계 조작 | 기기 시각 변경 · 비행기 모드 · 재설치 |
| 오프라인 복귀 | 1시간 / 1일 / 3일 / 30일 미접속 후 정산 정확성 |
| 알림 | 야간 금지(23~07) · 긴급 1일 5회 · 묶음 3회 |
| 세이브 이행 | 규칙 버전 넘김 · 중단 캠페인 복원 |
| 결제 | 중복 지급 · 지급 실패 · 환불 회수 |
| 밸런스 회귀 | 헤드리스 100회 자동 캠페인 (§9) |
| 현지화 | 문자열 넘침 · 미번역 검출 |

## 9. 첫 코드는 게임이 아니다 [권고]

`ai-design.md` §11이 이미 검증 도구 다섯을 열거하고 있다 — 결정 로그 · 고속 시뮬레이션 ·
역사 재현율 측정 · 세력 승률 분포 · 이벤트 발생률.

**이 다섯이 프로토타입의 첫 산출물이 되어야 한다.**

**근거**

1. **최대 미검증 위험은 그래픽이 아니라 밸런스다.** `CLAUDE.md` §5 함정 2 — 「대부분의 수치는 미검증」.
2. `ai-design` §11.1이 **이미 합격 기준을 숫자로 갖고 있다** — 역사 재현율 40~60% · 세력 승률 편차 3배 이내 ·
   미발동 이벤트 0종 · 조기 종료율 20% 이하. 시험 기준이 있는데 시험 도구가 없다.
3. **헤드리스 시뮬레이터는 §2.3의 시뮬레이션 코어를 그대로 쓴다.** 버려지는 코드가 아니라 본편의 심장이다.
4. 남은 검토 포인트 중 다수가 **논쟁이 아니라 측정으로 풀린다.**
   `combat` §10-13(적벽 분기 A 27.4%는 밀집 진형 성립을 전제한 상한) ·
   `ai-design` §12-1(명문형 AI의 결단 마비) · §12-2(절단 가치 과최적화) —
   전부 「몇 번 중 몇 번이나 일어나는가」의 문제다.

> **화면 하나 없이, 190년 시나리오가 AI 대 AI로 100회 자동 진행되어
> 세력 승률 분포가 출력되는 것** — 이것이 M0의 산출물이다.

### 10.3 예산 감각

인월 단가를 **월 900만원**(간접비 포함)으로 가정하면 내부 인건비 **약 30억원**.
여기에 외주 아트·사운드·현지화·서버 운영비가 별도로 **5~10억원** 규모로 붙는다.

> **축소판 대안** — 시즌 대전(M4)과 전용 그림을 포기하고 텍스트 중심으로 좁히면
> **6인 × 24개월 ≈ 145 인월(약 13억원) + 외주 약 3억원**까지 내려간다.
> 잃는 것은 멀티플레이와 시각적 화려함이고, **잃지 않는 것은 주제축 둘과 회랑 설계다.**

## 11. 검토 포인트

| # | 쟁점 | 비고 |
|---|---|---|
| 1 | ~~**서버 전제가 「오프라인 진행」과 모순되지 않는가**~~ | **해소 — `DECISIONS.md` V-24 결정 ③ (2026-08-24).** 모순되지 않는다 — 「오프라인 진행」은 *플레이어가* 접속하지 않아도 세계가 나아간다는 뜻이지, 서버가 없다는 뜻이 아니다. 다만 **연결이 끊긴 상태에서 무엇을 보여줄지**가 미정 |
| 2 | **지연 산출의 등가 요건** | 요건을 정확히 쓰면 **「동일한 명령 집합과 동일한 개입 이력이면 결과가 같다」**이다. 「접속 빈도와 무관」이 아니다 — 전투 개입(1~2회)은 **접속한 쪽이 유리한 것이 정당한** 설계이므로(`combat.md` §2.2), 그것까지 지우면 개입 자체가 금지된다. 금지해야 하는 것은 **계산 경로에 따른 차이**뿐이다. 막간이 난수를 쓰지 않는 정산이라는 점(`interludes.md` §2.2)은 이 요건에 유리하게 작용한다 |
| 3 | **등용 3중 판정이 확률 표시 대상인가** | 초빙권 자체의 확률은 명백히 대상이다. 그러나 「초빙권을 써도 천명이 낮으면 실패한다」는 설계는 **구매물의 기대 효용에 영향을 준다.** 법무 검토 필요 (§7.2) |
| 4 | **규칙 버전 고정의 유지 비용** | 규칙 집합을 몇 세대까지 동시 유지할 것인가. 무제한은 불가능하다 |
| 5 | **복귀 브리핑 템플릿 물량** | `ui-design` §9-4에서 이미 제기됨. 아직 산정되지 않았다 — 물량을 세는 것 자체가 선행 작업 |
| 6 | **부품 조합형 초상이 인물의 개성을 지우는가** | `HANDOVER.md` §4.4가 「규칙 기반 자동 산출은 서사적 개성을 못 담는다」고 이미 경고했다. 스탯에서 났던 문제가 아트에서 반복될 수 있다 |
| 7 | **시즌 시간 배율 ×0.25의 서버 비용** | 상시 틱이 네 배 빠르게 돈다. 시즌 동시 개최 수의 상한이 필요 |
| 9 | **자산 계승이 시즌을 유료 우위로 만드는가** | 싱글에서 초빙권을 많이 산 플레이어가 인물을 그대로 시즌에 들고 들어오면, **불가침 원칙 ③(「초빙 기회는 살 수 있으나 등용 성공은 살 수 없다」)이 싱글에서만 지켜지고 시즌에서는 무너진다.** 시즌 진입 시 천명을 초기화한다면 등용 판정이 다시 걸리므로 방어가 되지만, 그러면 「자산 계승」의 의미가 옅어진다. **계승 범위를 정하는 것이 곧 이 문제의 답이다** |
| 8 | **348시간 완주율** | 기획 위험이지만 **예산 위험이기도 하다.** 시나리오 6개 중 3개까지만 도달된다면 M3의 절반은 보이지 않는 콘텐츠다. 시나리오 단위 완결감 설계가 선행되어야 한다 |
