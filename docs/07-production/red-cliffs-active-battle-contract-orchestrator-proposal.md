목표는 같은 시드와 플레이어 입력에서 다음을 코어 권위로 재현하는 것이다.

## 2. 현재 구현과 결손

- `Campaign._arrive_fleets()`는 적 권역 도착 즉시 `_resolve_battle()`을 호출하고, 한 호출에서 5페이즈와 점령/패주를 끝낸다. `pending`/`active` 전투 권위 상태는 없다 (`core/campaign.gd:710-883`).
- 208의 Event 09/10/11, 조건 결과, 전투 전이, 뉴스 기록 모델은 코어에 없다. 현재 `events_fired`는 기능 이벤트의 횟수/쿨다운이다.
- `HomeMapSnapshot`의 `active_battles`, `red_cliff_conditions`, `news`는 `runtime` fixture이고 capability=false, provenance=`runtime_fixture` 또는 `unsupported`다 (`app/home_map_snapshot.gd:35-38, 112-117, 436-476`). 현재 화면의 적벽 표식은 fixture의 `BATTLE-RED-CLIFF`와 다섯 조건에 의존한다.
- 저장은 V-62의 시드+플레이어 명령 로그 재생이며, 지문은 활성 전투/뉴스를 아직 접지 않는다. 따라서 fixture 시험 617건은 코어 수직 흐름 완료 증거가 아니다.

## 3. 적벽 개전 정본과 미정값

### 확정 정본

208 ACT 7의 전용 `Event 09. 전제 조건 판정 [FIXED]`:

`조조 남하 완료 ∧ 손권 독립 유지 ∧ 유비 대조조 적대 ∧ 손유 군사협정 성립 ∧ 장강 방어선 형성`

하나라도 어긋나면 적벽은 발생하지 않는다. 다음 ACT 8의 `Event 10. 적벽 대회전 [LIKELY]`은 전역 8단계, 그 중 주력전은 태양계권 구지 궤도에서 일어난다. 결과 `Event 11 [FIXED]`가 뒤를 잇는다. 태양계권/구지는 전장 위치이지 사전 소유 필수 조건이 아니다. 101:46(2.20배)은 개전 게이트가 아니라 역사 검산의 문맥이다.

근거: `scenario-200-208.md` §7.2·§8 ACT 7~8·§10 검토 2, `combat.md` §4.3.3·§5.7, `DECISIONS.md` V-37·V-48.

적벽 미발생은 대체 대회전을 만들지 않고 즉시 조기 종료 판정으로 간다(DEC-01/V-48).

### 사건 ID

적벽은 F-01~F-40 중 하나가 아니다. F-07/F-08/F-09 등은 연합·교섭·분열 외교라는 주변 일반 기능 이벤트이고, Event 09/10/11을 대체하지 않는다. 별도 **시나리오 사건 식별 체계**와 전이 기록이 필요하지만, 문자열/번호는 아직 정본에 없으므로 이 문서는 임의 ID를 확정하지 않는다.

### 발주자 승인 결정

1. 지속형 전투는 **적벽에만 먼저 적용**하고, 일반 전투는 기존 즉시 해결을 유지한다.
2. Event 09/10/11은 F-01~F-40과 분리한 **208 전용 시나리오 사건 ID 체계**로 등록한다. 실제 문자열 형식은 기존 ID 관례를 조사하는 첫 코어 슬라이스에서 제안·검증한다.
3. 태양계권이 무주공산·분점·제3세력 소유여도, 다섯 개전 조건과 참가 함대 조건이 충족되면 구지 궤도 전장을 허용한다.
4. 101:46은 **역사 검산·회귀 기준**으로만 유지하며 새 개전 전력비 게이트를 만들지 않는다.
5. 지속형 적벽은 **새 ruleset 세대**로 격리하며, 기존 ruleset 저장의 재생 결과를 보존한다.
6. 적벽 전투가 `active`로 전이할 때 한 번만 C-02 긴급 인터럽트 배너를 표시한다. 다른 전이는 뉴스/브리핑 기록으로 남긴다.

### 여전히 구현 전에 구체화할 항목

1. 조조 남하 완료, 장강 방어선 형성, 참여 함대 도달의 정확한 코어 술어와 관측 경계.
2. Event 09/10/11의 실제 ID 문자열, 결과 열거값, 뉴스 템플릿 키.
3. DEC-01 즉시 종료와 일반 `_check_end()`의 동일 틱 우선순위.

### 구현용 진행 원장 결정

Event 03(조조 남하), Event 04(손권 선택), Event 06(유비 선택), Event 07(손유 회담)의 실제 시나리오 선택/결과는 `SCN-03` 전용의 결정론적 진행 원장에 기록한다. Event 07만이 손유 군사협정과 장강 방어선의 결과를 기록한다. Event 09는 이 원장이 제공하는 다섯 조건만 읽고, 권역 소유·전력비·UI 값·추정 외교 관계를 대신 읽지 않는다. 조건이 아직 기록되지 않은 경우는 false가 아닌 미확정이며 Event 09/DEC-01을 발화하지 않는다. 마지막 필수 선행 결과가 확정된 뒤 하나라도 false일 때만 DEC-01 조기 종료를 적용한다.

첫 코어 슬라이스의 사건 ID 형식은 `SCN-03-E09`를 사용한다. Event 10/11은 각각 같은 형식의 후속 ID로 예약하되, 활성 전투 구현 전에는 발화하지 않는다.

## 4. 사건·뉴스·활성 전투의 책임

| 구분 | 코어 책임 | 저장/표시 관계 |
|---|---|---|
| 시나리오 사건 | Event 09 조건 판정, Event 10 생성 요청, Event 11 결과 전이 | 발생 원인/전이 ID는 재생 가능해야 함 |
| 활성 전투 | 참가자·장소·페이즈·난수·손실·결과의 권위 게임 상태 | 저장/복원·지문·재생 대상 |
| 뉴스 | `created/activated/phase/resolved/cancelled` 전이에서 생기는 기록 | 전투 상태의 대체물이 아니며 refresh에서 재생성/중복 금지 |
| UI | 코어의 읽기 전용 투영 소비 | 조건·전투·관측·결과를 재계산하지 않음 |

## 5. 활성 전투 상태 전이

```text
없음 → pending → active → resolved
             └→ cancelled (시작 전 전제/참전자/장소 무효)
```

- `pending`: Event 10은 성립했으나 참가자·전장·시작 경계가 아직 고정되지 않은 상태.
- `active`: 시작 틱, 참가 함대 및 역할, 장소, 현 페이즈가 고정되어 진행 가능한 상태.
- `resolved`: 결과·종결 틱·손실/점령/패주 적용 사실이 하나로 확정된 종결 상태.
- `cancelled`: pending 뒤 시작 전 무효가 되었을 때만 사용하며 사유 코드를 보존한다. 별도 `invalidated`는 최소 계약에 불필요하다. active 뒤에는 임의 삭제가 아닌 resolved로 귀결한다.

지속형 전투는 적벽 전용으로 먼저 적용하고 일반 전투의 즉시 해결은 유지한다. 동일 틱 우선순위(도착·월정산·AI·사건·종료)는 첫 코어 슬라이스에서 정본/현행 순서를 대조해 확정해야 한다.

### 참가·개전 정본 보강 (발주자 승인)

- `cao_side`는 공격측, `sun_liu_side`는 방어측이다. 태양계권의 현 소유자는 어느 편도 정하지 않는다.
- Event 07 성공은 적벽 participant manifest를 기록한다. manifest에는 양측의 고정 함대 ID·역할과 권역 소유 없는 유비 시나리오 contingent가 들어간다. 자동 함대 선택·전력비·권역 소유 추론은 금지한다.
- Event 09 성공은 battle ID `SCN-03-E09-RED-CLIFF-01`의 `pending`을 한 번 파생한다. manifest의 필수 함대가 모두 `SYS-13`에 도달하면 역할·참가자·시작 tick을 동결하고, 전역 7단계에서 `active`로 전이한다.
- `campaign_stage`(1~8)와 `combat_phase`(1~5)는 별도 필드다. `active` 전에는 combat phase가 없다.
- 필수 함대 소멸, 명시 철수, manifest 무효, 시나리오 종료는 pending의 `cancelled` 사유 코드다. active는 `resolved`로만 종결한다.

## 6. 최소 데이터 구조와 ID 규칙

권위 `ActiveBattle` 최소 필드:

- 불변: `battle_id`, `cause_event_id`, `scenario_id`.
- 위치: `region_id`, `system_id`; 표시용 천체 앵커/좌표는 투영 데이터다.
- 참가: 공격/방어 주 세력, 동맹 참전 세력, 정렬·고정된 참가 함대 ID와 시작 역할.
- 시간/진행: 생성/활성화 tick, current phase, next phase tick 또는 마감 tick, 페이즈별 누적 손실·사기·잔여 효과.
- 종료: 종료 tick, 결과 코드, 손실·점령·패주 적용 사실, 관련 뉴스 전이 ID.
- 관측: viewer별 코어가 계산한 공개 단계/신선도만.

`battle_id`는 UI 문자열·객체 주소·표시 순서에 의존하지 않고, 재생에서 동일하게 생성되는 발생 원인과 결정론적 순번으로 유도한다. 정확한 포맷은 ID 체계 결정 후 등록한다.

## 7. 저장·복원·지문·재생 계약

V-62의 시드+플레이어 명령 로그 원칙을 유지한다. 활성 전투가 명시 틱 전이와 로그로 재구성 가능하면 직접 스냅숏 정본이 아니라 파생 상태다. 플레이어 전투 지시·취소·위임은 A-03 `World.issue` 경로를 거쳐 `origin != ai` 로그로 남는다.

- 재생은 동일 틱 순서로 사건 → pending/active → 페이즈 → 뉴스 전이를 재현한다.
- `Campaign.digest()`는 정렬된 전투 ID/상태/위치/참가자/시간/중간 상태/종결 결과와 보존할 뉴스 전이 ID를 접어야 한다.
- 뉴스 본문은 독립 정본으로 저장하지 않는다. 전이 ID와 템플릿 버전에서 파생한다. 본문 보존 기간/템플릿 버전 정책은 발주자 결정이다.
- 난수는 현 `(seed, domain, current_tick)` 새 스트림만으로 페이즈를 분할하면 안 된다. 시작 tick+전투 ID+phase+side+roll을 키로 하는 무순서 난수, 또는 재구성 가능한 시작 스트림 문맥 중 하나를 구현 전에 선택한다.
- 알고리즘/난수 키/전이 순서가 바뀌면 기존 로그 재생이 달라질 수 있다. 지속형 적벽은 새 ruleset 세대로 격리하고 기존 ruleset 재생 결과는 보존한다.

## 8. 관측·전쟁 안개 계약

`core/`만 viewer별 공개 범위와 신선도를 정한다. 아군은 정밀 소유·척수 등을 받을 수 있으나 적은 관측 단계가 허용한 위치·범위·편성만 받는다. 참여 함대도 적 사기·정확 척수·명령/도착 tick·원시 목표를 누출하지 않는다. `_fleet_readings`는 권위 전투 상태가 아닌 세션 파생 캐시다.

## 9. HomeMapSnapshot 소비 계약

코어 읽기 전용 투영은 다음만 제공한다.

- `active_battles[]`: battle/scenario ID, 상태, 지역·성계·표시 앵커, 표시명, 시작 tick, phase, 관측 가능한 양측 요약, `entry_available`.
- `red_cliff_conditions`: 다섯 조건의 true/false/**미확인(키 부재)** tri-state. 누락을 false로 바꾸지 않는다.
- `news[]`: 안정적 news ID, 발생 tick/표시 시간, 종류/우선순위/headline, battle/event 연결, 소비 상태.
- `capabilities`와 `provenance`: 이 세 필드는 최종적으로 `campaign_core`(또는 구체적 코어 경로)여야 한다. fixture/unsupported는 빈/확인대기 표현만 허용하며 G-10 완료 증거가 아니다.

지도는 위치·상태·관측 허용 표현만, 뉴스 패널은 뉴스 레코드만, C-02는 코어가 준 긴급도/기한/기본처리만, 전투 진입은 active battle ID와 `entry_available`만 읽는다.

## 10. 뉴스 패널·C-02·전투 진입

- 뉴스 패널은 전투 배열을 훑어 새 뉴스를 합성하지 않는다.
- C-02는 적벽 전투가 `active`로 전이할 때만 한 번 긴급 배너를 표시한다. 우선순위·응답 기한·기본 처리는 코어 계약으로 받아 표시하며, 세부 기한표는 DEC-07과 함께 구현 전에 확정한다.
- 적벽 잠금 카드는 조건 tri-state와 active 전투 존재만 표시하며, 예정된 역사 전투를 만들거나 표시하지 않는다.
- 전투 진입은 active 상태만 가능하고, 코어 battle ID를 전달한다. UI는 함대·경로·전술 명령 유효성을 선택/추론하지 않는다.

## 11. 의존성

| 항목 | G-10에 필요한 경계 |
|---|---|
| A-01 | 활성 전투가 재생 파생 상태인지 및 필요한 저장 경계 |

## 12. 단계별 구현 순서

1. 코어에서 Event 09 조건의 실제 술어, 시나리오 사건 ID 형식, DEC-01 종료 우선순위를 시험으로 고정한다.
2. 적벽 전용 전투 상태 기계·난수 앵커·전이 순서를 새 ruleset 세대에 도입한다.
3. 저장/지문/재생 및 관측 투영을 코어에서 검증한다.
4. HomeMapSnapshot을 core provenance로 교체하고 fixture 이행 장치를 제거/격리한다.
5. C-02/뉴스/전투 진입 UI와 1600×900 수용을 연결해 검증한다.

## 13. 검증 기준

- 단위: 조건 술어, 상태 전이, ID 중복 거부, pending 취소, active의 단일 resolved 종결, 관측 누출 차단.
- 통합: 같은 시드/입력에서 조건 충족 → 사건 → 뉴스 → active → 종료가 한 번씩, 같은 순서로 발생.
- 저장: pending, active, 페이즈 직전, 종료 직후 저장점의 복원·재생 결과와 digest 일치; 전이/명령 변조 실패.
- 회귀: 비적벽 즉시 전투의 기존 결과를 유지할지 또는 새 ruleset에 한정할지를 명시하고 시험한다.
- UI: fixture와 core 소비 시험을 분리한다. 미래 marker 없음, 조건만/전투만/둘 다/resolved/cancelled, fixture 비우선, news 중복 없음.
- 시각·입력: Windows 1600×900에서 기본 홈, 일부/미확인 잠금, active 지도 Z1~Z5, 뉴스 패널, C-02 배너가 다른 오버레이 위에 있는 상태, 전투 진입/종료 브리핑을 캡처·입력 검증한다. 1280×720·1920×1080 회귀를 권장한다.

## 14. 실패 시 롤백 경계

같은 입력의 digest 불일치, 복원 뒤 active/news 전이 불일치, 플레이어 입력의 로그 우회, 기존 ruleset 재생 변경이 확인되면 구현을 중단하고 계약으로 돌아간다. 롤백은 작업 자신의 작고 검증된 커밋의 역변경만 대상으로 하며, 공유 작업 트리에 reset/stash/clean/checkout 복원을 하지 않는다. fixture는 core 계약 검증 전까지 완료 증거로 승격하지 않는다.
