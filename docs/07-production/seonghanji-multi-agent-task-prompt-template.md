# 성한지 멀티 에이전트 작업 프롬프트 템플릿

> 목적: 성한지 프로젝트의 구현·안정화·검증·리뷰 작업을 새 채팅에서 실행할 때 사용하는 공용 프롬프트 정본.
>
> 사용법: 아래 **작업별 교체 구역**의 `{{...}}`만 현재 작업에 맞게 바꾼다. **고정 유지 구역**의 알림·참고·주의·완료 절차는 삭제하거나 완화하지 않는다.

---

## 1. 작업별 교체 구역

아래 값만 작업마다 갱신한다.

```text
{{CHAT_TITLE}}          = 새 채팅에 표시할 제목. 원칙적으로 Task ID + 공식 제목과 동일
{{TASK_ID}}             = 예: DEMO-RC-LT-04
{{TASK_TITLE}}          = 예: 적벽대전 데모 저장·이어하기 및 초반 안내
{{TASK_MODE}}           = 구현 / 안정화 / 검증 / 리뷰 중 하나
{{CURRENT_BASELINE}}    = 확인된 branch, HEAD, origin/main, 직전 Task 상태
{{BACKGROUND}}          = 이 작업이 필요한 실제 문제와 현재 동작
{{PLAYER_OUTCOME}}      = 완료 후 플레이어가 새로 할 수 있어야 하는 행동
{{GOAL}}                = 이번 Task가 달성해야 할 단일 목표
{{NON_GOALS}}           = 이번 Task에서 다루지 않을 범위
{{AUTHORITIES}}         = 반드시 읽을 정본 문서·데이터·코드
{{SUBTASKS}}            = 독립 시험 가능한 하위 Task ID + 공식 제목
{{AGENT_ASSIGNMENTS}}   = 에이전트별 책임·소유 파일·금지 파일
{{EXACT_CHANGES}}       = 함수/API/데이터/노드/UI 흐름별 구체 변경사항
{{ERROR_BOUNDARIES}}    = 거부·중복·복원·실패·잘못된 입력 처리
{{TEST_FILES}}          = 신규 또는 수정할 시험 파일
{{TEST_MATRIX}}         = 필수 정상·실패·저장·재생·중복 방지 시험 사례
{{REGRESSION_COMMANDS}} = 반드시 실행할 기존 회귀 시험과 명령
{{GUI_ACCEPTANCE}}      = 해상도·화면·입력·캡처·합격 기준
{{OUTPUT_DOCS}}         = 구현 계약·수용 보고서 경로
{{COMMIT_PLAN}}         = 하위 Task별 권장 커밋 메시지
{{DONE_CRITERIA}}       = 정량적 최종 완료 조건
{{NEXT_RECOMMENDATION}} = 완료 후 검토할 다음 기능 후보
```

작업별 내용을 채울 때 다음 원칙을 적용한다.

- “적절히 구현”, “필요하면 수정”, “충분히 시험” 같은 모호한 표현을 사용하지 않는다.
- 변경할 함수, 공개 API, 데이터 필드, UI 노드, 버튼 동작, 정상·거부 상태를 가능한 범위에서 명시한다.
- 각 하위 Task는 별도로 실행하고 PASS/FAIL을 판정할 수 있어야 한다.
- 테스트 파일 이름과 최소 수용 사례를 작업 시작 전에 고정한다.
- 플레이어가 실제로 새로 할 수 있는 행동이 없는 작업은 기능 구현 Task로 잡지 않는다.

[참고 — 프로젝트 권위와 개발 방향]

1. 이 프로젝트의 현재 우선 목표는 적벽대전 시나리오를 실제로 진행할 수 있는 데모 버전으로 완성하는 것이다.
2. CI·기반 정리보다 플레이어가 화면에서 수행하는 실제 기능을 우선한다. 단, 저장·결정론·회귀를 깨뜨려서는 안 된다.
3. 권위 계층은 다음과 같다.
   `data/schema → GameData → Campaign/World/core → read-only projection → UI`
4. UI는 이동, 전투, 사건, 저장, 승패, 도착 시간, 난수 결과를 직접 계산하거나 주입하지 않는다.
5. UI는 코어의 공개 API와 읽기 전용 projection만 소비한다.
6. 기존 canonical ID, 시나리오 의미, 저장·재생 계약, 결정론적 반복 순서를 유지한다.
7. 표시용 문자열이나 fixture를 게임 상태의 권위로 사용하지 않는다.
8. 정본에 없는 역사 설정, 수치, 사건 결과, 함대 구성, 엔딩 규칙을 임의로 만들지 않는다.
9. 3D가 채택된 프로젝트이지만, 개별 Task의 승인된 표현 정책과 현재 제품 코드를 먼저 확인한다. 오래된 문서 한 줄만으로 실시간 3D를 재도입하거나 제거하지 않는다.

[주의 — 작업 시작 전 필수 점검]

1. 작업 시작 시 다음을 기록한다.
   - 현재 branch
   - `git rev-parse HEAD`
   - `git fetch origin` 후 `git rev-parse origin/main`
   - `git status --branch --short`
   - 최근 관련 커밋
   - PROJECT-TRACKER.md 최상단
   - HANDOVER.md 최상단

2. 로컬이 원격보다 뒤에 있거나 작업 트리가 dirty이면 자동 pull, merge, rebase를 수행하지 않는다.
3. 원격 변경과 로컬 변경이 겹치는 파일을 먼저 식별하고, 사용자 작업을 보존할 통합 순서를 보고한다.
4. tracker나 handover에 적힌 PASS를 그대로 믿지 말고 커밋, 코드, 시험 결과와 대조한다.
5. 문서에 기록된 과거 시험 수치는 이번 실행 결과가 아니다. 직접 실행하지 않은 시험은 `미검증`으로 기록한다.

────────────────────────────────────────
[주의 — 공유 작업 트리와 Git 안전]

현재 작업 트리의 기존 수정·미추적 파일은 모두 사용자 또는 다른 세션의 작업으로 취급한다.

금지:
- `git reset --hard`
- `git clean`
- 광범위한 `git checkout --`
- 사용자 변경의 자동 stash
- `git add .`
- `git add -A`
- 무관한 파일의 삭제·이동·복원
- 다른 Task가 수정한 파일 덮어쓰기
- `.uid`, `.import`, `out/`, cache 파일의 일괄 추가
- 모델·텍스처·지도·셰이더·대형 binary의 무검토 추가

필수:
- 에이전트별 소유 파일을 작업 전에 선언한다.
- Task에서 직접 변경한 파일만 `git add -- <명시적 경로>`로 stage한다.
- 커밋 전 `git diff --cached --check`를 실행한다.
- 커밋 전 `git diff --cached --name-status`로 staged 목록을 검토한다.
- 무관한 기존 변경이 staged되면 커밋하지 않는다.
- 줄바꿈만 바뀐 대량 diff가 없는지 확인한다.
- 대형 binary는 크기·런타임 참조·라이선스·필요성을 확인하지 않으면 포함하지 않는다.

[고정 실행 절차]

Phase 0 — 기준선과 권위 확인
- Git 상태, 원격 차이, dirty 파일을 기록한다.
- tracker, handover, 관련 정본과 실제 구현을 읽는다.
- 기존 정상 경로와 알려진 실패를 재현한다.
- Task 범위, 비범위, 파일 소유권, 수용 조건을 동결한다.

Phase 1 — 계약과 시험 고정
- 정상 입력, 잘못된 입력, 중복 입력, 저장·복원, 재진입 경계를 정의한다.
- 공개 API, 반환 데이터, 상태 코드, UI 노드와 신호를 구체화한다.
- 구현 전에 신규 집중 시험의 파일명과 수용 사례를 확정한다.

Phase 2 — 기능 구현
- 가장 작은 코어 경계부터 구현한다.
- UI는 확정된 공개 계약 뒤에 연결한다.
- 기존 제품 경로를 재사용하고 중복 시스템을 만들지 않는다.
- 기능 구현 Task는 실제 플레이어 조작까지 연결한다.

Phase 3 — 집중 시험과 독립 QA
- 하위 Task별 집중 시험을 실행한다.
- 구현 담당과 다른 에이전트가 독립적으로 diff와 제품 경로를 검토한다.
- 시험이 private field, snapshot, 위치, 승패, 뉴스 등을 직접 주입해 통과하는지 감사한다.
- 실패를 assertion 삭제, 기준 하향, skip 증가로 숨기지 않는다.

Phase 4 — 회귀와 GUI 수용
- 지정된 기존 회귀 시험을 실행한다.
- 코어를 변경했다면 저장·복원과 명령 로그 재생을 확인한다.
- 화면 작업은 Windows Godot GUI와 지정 해상도에서 검수한다.
- 마우스와 키보드 공개 입력 경로를 확인한다.
- GUI 캡처는 `out/`에만 저장하고 커밋하지 않는다.
- 자동화할 수 없는 물리 입력은 자동 PASS와 섞지 말고 사람 스모크로 분리한다.

Phase 5 — 관리 파일, 커밋, push
- 구현 계약과 수용 보고서를 작성한다.
- PROJECT-TRACKER.md를 갱신한다.
- HANDOVER.md 최상단을 갱신한다.
- 변경 경로를 재검토한다.
- Task 관련 경로만 stage한다.
- 검증 가능한 단위로 커밋한다.
- `git push origin main`을 수행한다.
- push 후 HEAD와 origin/main SHA가 같은지 확인한다.

[상태 판정 규칙]

PASS:
- Task의 플레이어 결과와 구현 요구사항이 모두 충족됨
- 신규 집중 시험과 필수 회귀가 exit 0
- 필요한 GUI 수용 완료
- 독립 QA 완료
- 구현·수용 문서 완료
- PROJECT-TRACKER.md 갱신
- HANDOVER.md 최상단 갱신
- 경로 지정 커밋 완료
- push 완료
- `HEAD == origin/main`

PARTIAL:
- 기능 일부 또는 자동시험은 완료했지만 GUI, 회귀, 문서, 통합, push 중 하나가 남음
- 완료된 범위와 미완료 범위를 분리 기록

BLOCKED:
- 동일한 외부/환경 차단이 반복되고 안전한 우회가 없으며 사용자 결정 없이는 진행할 수 없음
- 차단 명령, 오류, 재현 횟수, 필요한 사용자 조치를 기록

금지:
- 시험 실패 상태에서 PASS
- GUI 미검수 상태에서 시각 수용 PASS
- push 실패 또는 SHA 불일치 상태에서 완료
- tracker/handover 누락 상태에서 완료
- 문서에 적힌 과거 결과만으로 현재 상태 PASS

[최종 보고 형식]

1. Task ID와 공식 제목
2. 작업 유형

## 4. 작업별 완료 조건 작성 규칙

`{{DONE_CRITERIA}}`는 다음 형태로 작성한다.

```text
- 플레이어가 {{화면/메뉴}}에서 {{행동}}을 직접 수행할 수 있다.
- 해당 행동은 {{공개 코어 API/명령}}을 통해서만 적용된다.
- {{상태 A}} 전에는 {{행동 B}}가 거부된다.
- {{상태 C}}가 되면 {{결과 D}}가 정확히 한 번 발생한다.
- 저장·복원 뒤 {{핵심 상태}}와 digest가 동일하다.
- 동일 seed·동일 command log는 동일 결과를 만든다.
- 신규 집중 시험 {{파일}}이 실패 0, exit 0이다.
- 지정 회귀가 실패 0, exit 0이다.
- Windows {{해상도}} GUI와 공개 입력 경로가 PASS다.
- tracker, handover, 문서, 커밋, push, SHA 확인이 완료됐다.
```

## 5. 템플릿 변경 관리

- 프로젝트의 모델, 실행 파일, 관리 절차, Git 안전 원칙이 바뀔 때만 고정 유지 구역을 수정한다.
- 개별 기능의 배경·목표·파일·시험·완료 조건은 고정 구역에 누적하지 않는다.
- 완료된 Task의 상세 내용을 이 템플릿에 기록하지 않는다. 완료 이력은 PROJECT-TRACKER.md와 HANDOVER.md가 담당한다.
- 새 작업 프롬프트를 만들 때는 이 파일을 복사하지 말고, 1절의 변수만 채운 완성 프롬프트를 채팅에 제공한다.
