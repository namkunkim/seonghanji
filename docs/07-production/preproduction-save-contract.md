## 0. 이 문서가 닫는 것

리스크 등록부 §2 2순위가 R-08(캠페인 저장·복원 공백)의 완화 순서를 다섯 단계로 적었다.
이 문서는 그 다섯 단계를 그대로 다섯 절로 옮긴다. 규칙 집합(ruleset)의 정의와 버전 고정은
`data-model.md` §5 가 정본이다.

| 리스크 §2 2순위 단계 | 이 문서 |
|---|---|
| 1. 현재 `World` 재생이 보장하는 범위와 보장하지 않는 캠페인 상태를 구분한다 | §1 |
| 2. 저장 대상에 세력·함대·경제·외교·이벤트·전투 결과·시간·규칙 집합 버전을 포함할지 명시한다 | §2 |
| 3. 스냅숏과 명령 로그의 경계, 규칙 버전 불일치, 손상 저장 복구 정책을 결정한다 | §3 |
| 4. 동일 시드·명령으로 저장 전후 세계 지문이 일치하는 인수 기준을 세운다 | §4 |
| 5. 이 계약이 승인되기 전에는 S3.8 UI 를 상세 설계·구현하지 않는다 | §5 |

GATE-PRE-03 의 닫힘 조건(리스크 §3.1)은 **「캠페인 저장 범위, 규칙 집합 버전, 스냅숏/로그
경계, 복원·오류 처리, 지문 검증의 인수 기준이 명시됨」**이다. 각 항목은 아래 절에 대응한다.

이 문서는 **결정을 대신 내리지 않는다.** 선택지와 권고, 그리고 미결로 남길 때의 처리를 적는다.
승인 시 `docs/DECISIONS.md` 에 V-항목으로 기록하는 것은 발주자 확정 후 P0-09 세션의 몫이다.

## 1. 현재 `World` 재생이 보장하는 것 / 보장하지 않는 캠페인 상태

### 1.1 사실 — 지금 코드가 무엇을 하는가

세이브는 `core/save.gd` 가 다룬다. `data-model.md` §5.4·V-25 ③ 대로 **「상태」가 아니라
「시드 + 명령 로그(command log)」**다.

| 함수 | 하는 일 | 근거 |
|---|---|---|
| `Save.to_dict(world)` | `ruleset` · `scenario` · `seed` · `game_tick` · `player_faction` · `capital` · `commands[]` 를 직렬화. `commands[]` 는 `seq`·`issued_tick`·`arrival_tick`·`kind`·`payload` | `core/save.gd:30`~`56` |
| `Save.write_file` | 위에 `save_version`(파일 형식 판, 현재 `1`) 을 더해 파일로 | `core/save.gd:125`~`132` · `schema/save.json` |
| `Save.replay(d, data, damage)` | **`World` 를 새로 만들고**, 명령을 전부 대기열에 되넣고, `Sim.step_ticks(w, game_tick)` 로 처음부터 재생 | `core/save.gd:63`~`87` |
| `Save.digest(world)` | 세계 상태를 하나의 정수로 접는다. 재생이 옳았는지 판정하는 근거 | `core/save.gd:96`~`117` |

`Save.replay` 가 부르는 `Sim.step_ticks` → `Sim._advance_one_tick` 은 **세 가지만 한다** —
① 도달한 명령을 `pending` → `applied` 로 옮긴다, ② 연 1회 전화 계수 회복(`_settle_year`),
③ AI 판단 횟수 계수 증가. **전투 해결·함대 이동·이벤트 판정은 `Sim` 에 없다**
(`core/sim.gd:51`~`58` 의 주석 「③ 함대 이동 — S3 에서 / ④ 전투 해결 … 진행 루프는 S3 /
⑥ 이벤트 판정 … 미착수」).

### 1.2 구분표

| 캠페인 상태 | 현재 `World` 재생이 보장하는가 | 근거 / 비고 |
|---|---|---|
| 게임 내 경과 틱 · 진행 횟수(`tick_count`) | **보장** | `tests/run_tests.gd:831`~`832` — 재생 후 일치 |
| 규칙 집합 버전 · 시나리오 · 시드 · 본거지 · 플레이어 세력 | **보장** (스칼라 그대로 복원) | `core/save.gd:66`~`70` |
| 명령 로그(발행·도달 시각 · 발행 순번 · payload) | **보장** | `core/save.gd:73`~`84` · 순번 정렬 후 재적재 |
| 권역 전화 계수(`war_damage_milli`) 회복 진행분 | **보장** | `core/sim.gd:65` 연 정산 · `tests/run_tests.gd:842`~`843` |
| 권역 `development` · `garrison` · `recovery_investment` · `owner` | **부분** — `digest` 는 접지만, `World` 단독 재생에는 이 값을 바꾸는 경로가 **연 정산 외에 없다** | 개발·징병·건조 효과는 §1.3 참조 |
| 내정 명령의 **효과**(개발·징병·수송·기술·위임·건조) | **보장 안 함** | `Sim._deliver_commands` 는 명령을 옮기기만 한다. 효과는 `Campaign._apply_arrived`(`core/campaign.gd:461`)가 붙이며, `Save.replay` 는 이를 부르지 않는다 |
| 세력(`Faction`) — 자금 · 천명(Mandate) · 기술 · 보유 권역 · 통치 체제 · 황제 보유 · 할거 시계 · 패권 압력 · 생존 여부 | **보장 안 함** | `core/campaign.gd:29` 에만 있고 세이브·재생 경로에 없음 |
| 함대(`Fleet`) — 존재 · 척수 · 사기 · 제독·참모 임명 · 훈련도 · 진형 · 위치 · 이동 중 목표·도달 시각 | **보장 안 함** | `core/campaign.gd:31` · `_spawn_fleet` 이 캠페인 셋업에서만 생성 |
| 외교(`Diplomacy`) — 신뢰도 · 단계 · 참전 의무 · 배신 기록 | **보장 안 함** | `core/campaign.gd:38` |
| 기능 이벤트 상태 — 발동 횟수(`events_fired`) · 재발동 쿨다운 · 동맹 성립 시각 | **보장 안 함** | `core/campaign.gd:47`·`52`·`53` |
| 인물 로스터 배치·임명 | **보장 안 함** | `core/campaign.gd:27` · `Roster.build` 가 셋업에서만 |
| 전투 결과 — 권역 점령으로 인한 `owner` 변경 · 함대 소멸 | **보장 안 함** | `_resolve_battle`·`_capture`(`core/campaign.gd:659`·`975`)는 캠페인 진행 루프에만 |

### 1.3 핵심 결손 두 가지

1. **캠페인을 직렬화·재생하는 경로 자체가 없다.** `Campaign` 에는 `to_dict`·`digest`·
   `Save.*` 호출이 하나도 없다(`core/campaign.gd` 전수 확인). `Save.replay` 는 `World`
   만 만든다. 따라서 「시드 + 명령 로그」로 캠페인을 되살리려면 `Campaign.step()`
   (`core/campaign.gd:415`)을 재생 루프로 쓰는 경로를 **새로 만들어야 한다.**
2. **`World` 단독 재생은 경제·전투·외교·이벤트를 재현하지 않는다.** `Save.replay` 로
   복원되는 것은 시간·명령 로그·전화 계수 회복까지다. 5.8개월짜리 캠페인의 나머지는
   전부 `Campaign` 계층에 있고, 그 계층은 재생 대상이 아니다.

> **결론:** 리스크 R-08 의 「현재 세계 단위 명령 재생이 장기 캠페인 저장·복원을 보장한다고
> 오인한다」는 정확한 진단이다. 현재 보장 범위는 **시간 모델 + 명령 로그 + 권역 전화 계수**
> 이며, 그 밖의 캠페인 상태는 저장되지도 재생되지도 않는다.

## 2. 저장 대상 명세 — 포함 / 제외 / 파생(재계산)

### 2.1 분류 원칙

`data-model.md` §4 「값을 두 곳에 두지 않는다」를 적용한다.

| 분류 | 뜻 | 예 |
|---|---|---|
| **포함** | 세이브 파일에 직접 기록한다. 그것 없이는 결정론(determinism) 재생이 성립하지 않는 입력 | 시드 · 명령 로그 · 규칙 집합 버전 |
| **파생(재계산)** | 저장하지 않는다. 포함 항목에서 재생으로 **다시 만들어진다.** 저장하면 §4 정본화 원칙 위반이고, 저장값과 재생값이 갈라지는 순간 조작 탐지가 무력해진다 | 세력 자금 · 함대 척수 · 천명 · 전투 결과 |
| **제외** | 저장도 재생도 하지 않는다. 진단·통계용이며 세계 상태가 아니다 | `schemes_tried` 등 계측 계수 |

> **원칙:** 「시드 + 명령 로그」 모델에서 **결정론적으로 재생 가능한 모든 것은 파생**이다.
> 포함 목록은 최소로 유지한다. 스냅숏(snapshot)을 도입하기로 결정하면(§3), 스냅숏은
> **파생 항목의 캐시**이지 새로운 정본이 아니다 — 스냅숏과 로그 재생이 어긋나면 로그가 이긴다.

### 2.2 도메인별 분류

리스크 §2 2순위 2단계가 나열한 여덟 도메인.

| 도메인 | 분류 | 근거 / 조건 |
|---|---|---|
| **시간** (경과 틱 · 진행 횟수) | **포함** | `game_tick` 은 이미 세이브에 있다(`schema/save.json`). 고정 스텝 누적이며 기기 시계를 읽지 않는다 |
| **규칙 집합 버전** | **포함** | `data-model.md` §5.3·§5.4 확정 — 세이브에 각인. 재론하지 않는다. §3.2 가 불일치 처리를 다룬다 |
| **명령 로그** | **포함** | `seq`·`issued_tick`·`arrival_tick`·`kind`·`payload`. 재생이 순서를 되살리는 유일한 키 |
| **세력**(자금 · 천명 · 기술 · 보유 권역 · 통치 체제 · 황제 보유 · 할거 시계 · 패권 압력 · 생존) | **파생(재계산)** | 전부 셋업(`Campaign.scenario_03`)의 확정 초기값 + 명령·AI·월 정산의 결정론적 함수. 저장 대상이 되려면 「명령 로그만으로 재생 불가능한 비결정 요소」가 있어야 하는데 현재 없다 → §4 인수 시험으로 확인 |
| **함대**(척수 · 사기 · 제독·참모 임명 · 훈련도 · 진형 · 위치 · 이동 중 상태) | **파생(재계산)** | 셋업의 실동원 비례 생성 + 임명 규칙(통솔 내림차순, 순서 고정) + 전투·이동의 결정론적 결과. **단, 플레이어 함대 명령(이동·분할·합류·편성·임명)이 전부 명령 로그에 들어가는지 미검증** → §3.4 검토 포인트 |
| **경제**(권역 개발·징병·전화 계수 · 세력 수지) | **파생(재계산)** | 내정 명령 효과 + 연 정산 + 월 정산. `war_damage_milli` 회복은 이미 `World` 재생으로 재현됨(§1.2). 나머지는 캠페인 재생 경로가 서면 함께 재현 |
| **외교**(신뢰도 · 단계 · 참전 의무 · 배신 기록) | **파생(재계산)** | `_ai_grand` 의 결정론적 판정 + `_capture` 의 참전 거부 기록. 시드·명령·틱의 함수 |
| **이벤트**(발동 횟수 · 재발동 쿨다운 · 동맹 성립 시각) | **파생(재계산)** | `_check_events` 가 시드 기반 난수로 판정. 쿨다운·성립 시각은 재생 중 다시 채워진다 |
| **전투 결과**(권역 점령 · 함대 소멸) | **파생(재계산)** | `_resolve_battle` 이 `world.rng(DOMAIN_COMBAT)` 로 굴린다. 난수 소비 순서가 고정(V-31)이므로 재생 시 동일 결과 |

### 2.3 이 분류가 성립하기 위한 전제

**모든 파생 항목이 「시드 + 명령 로그」만으로 재생 가능하다**는 것은 **가설**이다. 현재
`World` 단독 재생으로는 검증할 수 없다(§1.3). 성립 조건 셋:

1. 캠페인 재생 경로(`Campaign` 을 셋업부터 목표 틱까지 다시 돌리는 경로)가 존재한다.
2. 플레이어가 캠페인 중에 내리는 **모든** 명령이 명령 로그에 기록된다 — 내정뿐 아니라
   함대 이동·분할·합류·편성·임명·전술 지시까지. (현재 로그에 남는 것은 `World.issue`/
   `issue_to` 를 지난 명령뿐이다.)
3. AI 판단·전투·이벤트에 **기기·플랫폼 의존 비결정 요소가 없다** — 부동소수 금지, 난수
   소비 순서 고정, 컬렉션 순회 순서 고정(`dev-requirements.md` §2.3).

셋 중 하나라도 깨지면 해당 도메인은 **파생에서 포함으로 승격**해야 한다. 그 판정은 §4 의
지문 인수 시험이 내린다.

### 2.4 미결 시 처리

플레이어 함대 명령의 로그 기록 여부(전제 2)가 GATE-PRE-03 승인 시점에 확인되지 않으면,
**함대·전투 결과 도메인을 잠정적으로 「포함(스냅숏)」으로 두고**, 캠페인 재생 경로가 선
뒤(A-01) 전제 2·3 을 시험해 파생으로 내리는 것을 목표로 한다. 이 잠정 조치는 세이브 파일
크기를 키우므로 영구화하지 않는다.

## 3. 스냅숏 대 명령 로그 경계

### 3.1 무엇이 로그 재생이고 무엇이 스냅숏인가

| 방식 | 뜻 | 대가 |
|---|---|---|
| **순수 명령 로그 재생** (현재) | 세이브 = 시드 + 명령 로그. 불러오기 = 셋업부터 목표 틱까지 재생 | 용량 최소 · 조작 탐지 쉬움 · 버그 재현 쉬움. **불러오기 시간이 캠페인 길이에 비례** — 5.8개월분이면 재생이 길다(`core/save.gd:17` 주석) |
| **스냅숏 + 꼬리 로그** | 주기적으로 세계 상태 전체를 캐시하고, 그 이후의 명령만 로그로 | 불러오기 빠름. **용량 증가 · 스냅숏과 로그가 갈라질 위험**(§2.1) · 스냅숏 형식이 규칙 집합 버전에 묶임 |
| **경계 스냅숏만** | 시나리오 경계에서만 스냅숏을 남기고, 경계 사이는 순수 로그 재생 | 절충. 경계가 이미 규칙 승격 지점(§3.2)이라 자연스럽다. 경계 사이 최장 구간이 재생 상한 |

### 3.2 규칙 집합 버전 불일치 처리 — `data-model.md` §5.3 을 그대로 따른다

**이 항목은 확정 사항의 적용이지 새 결정이 아니다.** `data-model.md` §5.3:

- **patch** (`RS-x.y.Z`) — 결과가 바뀌지 않는다. 경계를 기다리지 않고 **즉시 적용**. 불러오기
  시 세이브의 `ruleset` patch 자리가 현재보다 낮아도 그대로 로드한다.
- **minor** (`RS-x.Y.z`) — 밸런스가 바뀐다. **다음 시나리오 경계에서만 승격.** 캠페인
  도중에는 세이브에 각인된 버전으로 계속 재생한다. 따라서 로더는 **여러 minor 세대를
  동시에 보유**해야 한다(§3.3).
- **major** (`RS-X.y.z`) — 세이브 호환이 깨진다(스키마 변경). **진행 중 캠페인에 적용하지
  않는다.** 로더는 major 불일치를 감지하면 자동 로드를 거부하고, 별도 마이그레이션 절차로
  넘긴다(현재 미작성 — `data-model.md` §미작성 「세이브 마이그레이션 절차」).

로더 판정 순서(권고):

```
세이브.ruleset 파싱 실패           → 손상 저장으로 처리 (§3.5)
major(세이브) ≠ major(현재)        → 로드 거부 · 마이그레이션 안내
minor(세이브) < minor(현재)        → 세이브 버전의 규칙 집합을 로드해 재생.
                                     다음 시나리오 경계에서 현재로 승격
minor(세이브) > minor(현재)        → 로드 거부 (더 새 빌드로 만든 세이브)
그 외 (major·minor 일치)           → patch 무시하고 로드
```

### 3.3 동시 유지 세대 수 — `data-model.md` §5.5 의 방식만 재확인

숫자는 지금 정할 수 없다(ACT 소요 실측 전). 방식:

```
동시 유지 minor 세대 수  ≥  (시나리오 경계 사이 최장 구간)  /  (minor 패치 주기)
```

경계 스냅숏(§3.1)을 채택하면 이 값이 「캠페인 전체 / 패치 주기」에서 「경계 사이 최장 구간 /
패치 주기」로 내려간다. GATE-PRE-04(QA 전략)의 밸런스 기준선 보존 방식과 같은 표를 공유한다.

### 3.4 권고와 미결

| 항목 | 권고 | 미결 시 처리 |
|---|---|---|
| 재생 방식 | **경계 스냅숏 + 경계 사이 순수 로그 재생.** 규칙 승격 지점과 스냅숏 지점을 일치시키면 스냅숏 형식이 규칙 집합 버전에 묶이는 문제가 경계에서만 발생 | 순수 로그 재생 유지. 불러오기 시간이 실측(A-01)에서 허용 밖이면 그때 스냅숏 도입 |
| 세이브 슬롯 중 자동 저장 주기 | 게임 내 1개월(월 정산 시점)마다 명령 로그 플러시 + 경계에서 스냅숏 | 수동 저장만. 크래시 복구 범위는 마지막 수동 저장까지 |
| 플레이어 함대 명령의 로그화 | **모든** 플레이어 명령이 `World` 명령 경로를 지나도록 A-03(명령 산정·검증 코어 이동)에서 강제 | §2.4 잠정 조치(함대·전투 결과 포함) |

## 4. 지문(fingerprint) 인수 기준

### 4.1 현재 지문이 무엇을 접는가

`Save.digest`(`core/save.gd:96`~`117`)가 정수 하나로 접는 것:

- `clock.tick` · `tick_count` · `rng_seed`
- `applied`·`pending` 명령 수 · `hash(ruleset + "|" + scenario)`
- **정렬된 권역 ID 순회**로 각 `RegionState` 의 `war_damage_milli` · `development` ·
  `garrison` · `recovery_investment` · `hash(owner)`
- 각 `applied` 명령의 `seq` · `arrival_tick`

**접지 않는 것:** 함대(척수·사기·임명·진형·위치) · 세력(자금·천명·기술·보유 권역) ·
외교(신뢰도·단계) · 이벤트 발동 상태 · 로스터 임명. → 현재 지문은 **권역·시간·명령 로그
계층만** 인증한다.

현재 시험은 `tests/run_tests.gd:801`(§25 「재생 — 저장 전과 같은 세계인가」) 하나이며,
`World` 에 내정 명령 3건을 3년 돌린 뒤 지문 일치와 전화 계수 재현, 그리고 시드·도달 시각을
1 바꾸면 지문이 갈리는지를 본다. **캠페인을 돌리는 시험이 아니다.**

### 4.2 캠페인 단위로 확장하는 인수 조건

| # | 조건 | 판정 방법 |
|---|---|---|
| 1 | **캠페인 지문이 존재한다** | `Campaign` 에 `digest()` 를 추가 — §4.3 의 필드를 정렬된 순회로 접는다 |
| 2 | **저장 전 = 재생 후** | 같은 시드·명령 로그로 셋업부터 목표 틱까지 재생한 `Campaign` 의 지문이 저장 시점 지문과 같다 |
| 3 | **입력 1 비트를 바꾸면 지문이 갈린다** | 시드 · 임의 명령의 `arrival_tick` · `payload` 를 1 바꾸면 재생 지문이 달라진다(현재 §25 가 `World` 에 대해 하는 검사의 캠페인판) |
| 4 | **중간 저장·복원이 최종 지문을 바꾸지 않는다** | 틱 T 에서 저장 → 새 프로세스에서 복원 → 종료까지 진행한 지문이, 저장 없이 끝까지 진행한 지문과 같다 |
| 5 | **경계 스냅숏(도입 시)이 로그 재생과 일치한다** | 스냅숏에서 복원한 지문 = 같은 틱까지 순수 로그 재생한 지문. 불일치 시 로그가 정본(§2.1) |
| 6 | **규칙 세대 격리** | minor 가 다른 두 빌드에서 같은 세이브를 로드하면, 세이브 버전의 규칙 집합으로 재생하는 한 지문이 같다(§3.2) |
| 7 | **크로스 플랫폼** | 안드로이드 실기와 개발 머신에서 같은 세이브의 재생 지문이 같다(`dev-requirements.md` §8 「결정론」 행) |

### 4.3 캠페인 지문이 접어야 하는 필드 (권고 목록)

정렬된 순회로만 접는다(`data-model.md` §2.3 · `core/save.gd:96` 주석 「Dictionary 순회 금지」).

- **세력** (정렬된 `faction_ids`): 자금 · 천명 · 기술 3축 · 보유 권역 수(또는 정렬된 권역 ID
  해시) · 패권 압력 · 할거 시계 · 생존 여부
- **함대** (정렬된 `fleet.id`): 소유 · 위치 · 척수 · 사기 · 훈련도 · 진형 · 제독·참모 ID ·
  이동 중이면 목표·도달 시각
- **외교** (정렬된 세력 쌍): 단계 · 신뢰도 · 참전 의무
- **이벤트**: 정렬된 이벤트 ID 별 발동 횟수
- **권역**: 현행 `Save.digest` 가 접는 다섯 필드 유지 + `stability`
- 기존 `Save.digest` 의 시간·명령 로그 부분 그대로 포함

> **제외:** 진단 계수(`schemes_tried` · `ambush_by_*` · `skip_*` 등). 세계 상태가 아니라
> 계측이며, 밸런스 조정 중 수시로 바뀐다. 이것을 지문에 넣으면 규칙 조정마다 인수 시험이
> 깨진다.

### 4.4 verify 계열과의 관계

검산기 셋(`verify_power` · `verify_budget` · `verify_chibi`)은 **문서값 대 코드 재계산**을
대조한다 — 「코드가 문서대로 계산하는가」. 지문 인수 시험은 **재생 대 원본**을 대조한다 —
「재생이 결정론적인가」. 둘은 목적이 다르며 서로를 대체하지 않는다. 저장·복원 계약은
**후자**만 다룬다. 다만 A-02 는 두 계열을 같은 CI 층(GATE-PRE-04 · Q-05)에 함께 둔다.

### 4.5 미결 시 처리

캠페인 재생 경로(A-01)가 서기 전에는 조건 1·2 를 만족시킬 수 없다. GATE-PRE-03 승인은
**「인수 조건 표(§4.2)가 A-01·A-02 의 완료 기준으로 채택됨」**을 뜻하며, 시험 자체의 통과는
개발 착수 후 첫 기반 묶음에서 판정한다. `PROJECT-TRACKER.md` A-02 의 완료 기준
(「정상 저장은 동일 지문, 변조 저장은 불일치가 시험으로 확인됨」)에 §4.2 표를 연결한다.
